## What is Test-Driven Development (TDD)

I have been reading the book <em>Test-Driven: TDD and Acceptance TDD for Java Developers</em> by Lasse Koskela which you can find [here](https://www.amazon.com/Test-Driven-Acceptance-Java-Developers/dp/1932394850) and is a much more comprehensive guide to using this practice, that I recommend every developer checks out. With that out of the way I'm going to do my best to summarize the main ideas of the practie and talk about my experience of how this has reinvigorated Test-Driven Development (TDD) is the concept of writing a test first and then <br>only</br> writing the code necessary to make that test pass. More specifically it is a cycle with three steps: test, code, refactor. 

## Writing Tests
During the test phase you write a failing test that will implicitly enforce design decisions into the implementation. Before I started learning about TDD I had a lot of trouble trying to design the architecture for even a small program all at once and found myself simply implementing different features all over the place and hoping to get the desired output when I finally tried to run the program. The iterative approach to TDD makes it much easier for me to come up with a features that I can write a set of tests for rather than starting with a design of the entire system.
